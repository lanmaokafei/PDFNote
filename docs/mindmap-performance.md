# 大画布性能：1483 张卡从 8.4 秒到 0.9 秒

导入 AnkiDroid 牌组后，单个画布可能有 1400+ 张卡片。0.21.0 之前打开这类画布要 8 秒以上才能看到第一个节点，堆内存 215MB，拖动画布也会掉帧。本文记录实测数据、根因和最终方案。

## 结论先行

**不是「数据太大」，而是「一次把 1483 个节点全挂到 DOM 上」。** 分栏视图里右栏只有 700px 宽，缩放 0.9 时同屏只放得下三四个节点，另外 1480 个节点纯属白渲染。

方案是**视口裁剪（viewport culling）**，不是「先加载、不显示」：

- 数据照旧一次性读进内存（IPC 只要 14ms，不是瓶颈）；
- 只挂载当前视口内的节点 DOM，滚动 / 平移时按需挂载；
- 节点数据、坐标、选中、折叠状态仍是完整的，`fitView`、导出、复习、AI 解析都不受影响。

「先不渲染」听起来更省，但要自己维护「哪些节点该出现」，一旦用户平移就得整层重建，还会破坏 React Flow 的测量与 #185 约束。裁留在 React Flow 内部完成（`onlyRenderVisibleElements`），等于把同一件事交给它做。

## 根因

| # | 问题 | 代价 |
| --- | --- | --- |
| 1 | 1483 个节点全部挂载，DOM 元素 33,745 个 | 首次可见 8.4s，堆 215MB |
| 2 | 每个节点用 store selector 扫全表算子节点数：`Object.values(cardsById).filter(...)` | O(n²) = 220 万次过滤，每次 store 更新重跑，单个长任务 3.7s |
| 3 | 每次 `refresh` 无条件 `buildTreeLayout(全部卡片)`，再串行取画布列表 | 打开已排版的画布也要重排一遍 |
| 4 | MiniMap 为 1483 个节点各画一个缩略矩形，每次节点变化全量重算 | 独立视图持续掉帧 |
| 5 | 大纲视图一次挂载 1483 行（每行两个可展开字段 + KaTeX） | 切大纲卡住数秒 |
| 6 | 首次加载 `fitView` 覆盖全部 1483 节点 | 缩放被压到 0.15 下限，等于什么都没看到 |

## 改动

### 1. 视口裁剪

```tsx
// MindmapWorkspace.tsx
onlyRenderVisibleElements={nodes.length > 60}
```

小画布（≤60 节点）保持原样，避免为几个节点引入视口计算；大画布只挂视口内的节点。

为了让未挂载的节点也能参与边线端点、命中测试与 `fitView`，给每个节点补了估算尺寸：

```tsx
width: size?.width ?? (compact ? 228 : 254),
height: size?.height ?? 172,
```

节点一旦挂载，`measured` 会覆盖估算值，既有的「只回写首次与 >24px 变化」的熔断逻辑不变。

### 2. 子节点数从 O(n²) 降到 O(n)

之前每个节点自己扫全表：

```tsx
// 旧：每个节点都跑一次 O(n) 过滤
const childCount = useCardStore((state) => Object.values(state.cardsById)
  .filter((candidate) => candidate.surface_mindmap && candidate.parent_id === data.card_id).length)
```

现在由工作区预算一张 `父 → 子数量` 表，通过 `MindmapNodeContext.childCounts` 下发，节点只做 `Map.get`。

### 3. 只在缺坐标时才重排

`refresh` 先按画布把已有坐标填好，只有真的缺坐标的卡片才触发 `buildTreeLayout`；画布列表也并入同一个 `Promise.all`，少一次串行往返。

### 4. 大图不做「全量适配」

- 首屏：节点数 > 400 时不再自动 `fitView`，停在左上角（分组根节点所在处），提示可用「适应视图」。
- 「适应视图」：大图只框住前 40 个节点，保证缩放后文字可读。
- Anki 导入后：超过 400 张不再全量重排 + 写回 1400 多行布局（后端导入本身已按牌组层级给了坐标）。

### 5. 大纲按需追加

首屏只挂 200 行，底部「继续显示（还有 N 行）」按 200 行追加；另外大纲森林只在切到大纲视图时才构建。

### 6. MiniMap 阈值

节点数 > 400 时不渲染 MiniMap（独立视图）。

## 实测

同一份 mock 数据（1483 张卡，其中 370 张带摘录图），`scripts/mindmap-regression.mjs` 的 `STEP=perf`：

| 指标 | 优化前 | 优化后（生产构建） |
| --- | --- | --- |
| 点击文档 → 第一个节点可见 | 8,437 ms | 898 ms |
| 挂载的节点 DOM | 1,483 | 3 |
| 总 DOM 元素 | 33,745 | 474 |
| 最长长任务 | 3,679 ms | 429 ms |
| 堆内存 | 215 MB | 60 MB |
| IPC 取数 | — | 14 ms |
| 前端计算 | — | 15 ms |

3 张卡的地板值是 150ms / 97ms（paint），也就是说 1483 张卡相对小画布只多花约 0.75s，其中大头是 React Flow 对 1483 条节点记录做的一次性初始化，而不是渲染。

## 回归

```bash
npm run dev -- --host 127.0.0.1
STEP=perf CARD_COUNT=1483 node scripts/mindmap-regression.mjs
```

脚本会断言：>200 张卡时挂载的 `.mindmap-node` 不超过 80 个 —— 有人不小心把裁剪关掉会立刻失败。其余 18 个既有场景（含 120 卡全量）保持不变。

## 还能怎么做（暂未做）

- **按画布取卡**：现在 `list_cards` 仍返回全库卡片，画布只做过滤。库里有上万张卡时可以把查询改成 join `mindmap_layout`，只取当前画布。
- **视口外不建边**：1483 条边的对象数组仍是全量构建，可改为只构建可见边（需要自己维护 viewport 订阅）。
- **虚拟化大纲**：目前是分页追加，改成窗口化可以做到任意行数恒定 DOM。
